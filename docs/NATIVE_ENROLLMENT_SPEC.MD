## Product contract

Separate explicit native enrollment is accepted. Ordinary packet-only installations and their signed updater staging, health check, restart and rollback behavior must remain unchanged. Trusted protected absence means NOT ENROLLED and nativeUnavailable; it is never a new packet-start prerequisite. Enrolled pending or unsafe state refuses participating protected admissions, including requests from the foreground process itself. Abnormal native failure may require explicit administrative recovery. Routine successful installation must not leave a manual-settlement lockout.

There is no enrollment command in this subset. Do not add a publication path, helper, setup wrapper, runtime writer, settlement endpoint, generic bypass, ignoreBarrier boolean or verified=true completion argument. Do not wire the model into current Core commands, Engine, windowsnet.Acquire, service updater, or Desktop. Existing experimental native source behavior is not newly enabled or globally disabled by these primitives; deployment of enrolled native support remains gated. This change alone enforces no production admission.

## Why enrollment is still refused

The connect mutex is thread-owned. DLL module pinning does not keep an MSI host alive; its death loses exclusion while outer rollback may continue. A commit callback may run before later rollback. RollbackDisabled can skip both commit and rollback actions. RemoveExistingProducts child removal must not settle an outer transaction. InstallFinalize can be a local boundary. MsiBeginTransaction/MsiEndTransaction require a real outer owner; an arbitrary DLL callback is not one. No authorized helper/wrapper or established safe outer terminal authority exists here.

The signed updater starts the replacement ordinary service to perform IPC health checks and restarts the restored ordinary service on rollback. A global pending refusal would break that contract. Settling before restart creates an unsafe gap. Old restored binaries ignore enrollment and may outlive updater death. Observing processes/markers is not enforcement. Until a future enrolled updater transaction proof preserves these semantics across success, failure, rollback and updater death, REFUSE ENROLLMENT; do not redesign the updater in this subset.

Future enrollment must also establish that every runnable managed network/recovery host participates, reject old/incompatible runnable hosts and prevent their later return through rollback. Enumeration, compatible version claims, installation markers and a one-time check cannot establish that. Proxy coverage is not claimed. Administrator compromise is outside the boundary, but ordinary users must not be able to redirect or erase enrollment state.

## Historical storage decision and limits (superseded below)

Choose a machine registry value as the future minimal durable representation: native HKLM SOFTWARE view, `SOFTWARE\Bimeron\Core\NativeEnrollment`, value `Record`, REG_BINARY. Use the OS-native view explicitly (64-bit on supported 64-bit Windows, including a 32-bit reader); never merge/fall back to WOW6432Node or HKCU. No registry key/value is created by this change. Registry fits one bounded record and handle-based security inspection; a file would add path/reparse/ancestor pinning. Neither gives outer transaction authority or automatic crash settlement.

Defer even a read-only Windows registry adapter: there is no authorized production caller and trustworthy absence is not equivalent to RegOpenKey failure. Implement the security/view/generation model and deterministic observations first. A later reader needs its own accepted contract and fixture evidence, not a silent expansion of this subset.

Trustworthy absence requires an authenticated native machine hive/view and a securely opened nearest existing ancestor chain that prevents untrusted create/delete/replace of the missing key/value. Only exact not-found at the intended location with that protection established is absence. Access denial, unknown view, broken chain, key deletion/recreation races, link redirection, query failure, missing value under an unexplained enrolled container, and unreadable security are Unsafe. An unprovisioned but securely protected vendor parent may establish non-enrollment; a generic missing subkey cannot. This model cannot remember that a privileged actor deleted an entire enrolled subtree. It claims no defense against malicious administrators or offline registry rollback.

Future registry security: owner SYSTEM or Builtin Administrators, present non-null protected DACL; reject unknown effective ACE forms and effective untrusted mutation rights (set value, create subkey, create link, delete, WRITE_DAC, WRITE_OWNER, generic write/all). Expand generic rights for registry objects. Read-only access is harmless. Validate inherited effective rights and every ancestor able to replace the child; do not copy the kernel-mutex access mask. TrustedInstaller ownership is not accepted for this new record contract without a spec change. Unsafe security cannot be converted to absence or repaired by a reader.

## Exact offline subset

Use one small platform-neutral internal package, `internal/nativeenrollment`, no new dependencies. Two production-source files at most (model/codec), focused tests and a short package comment. It is deliberately unconnected to production. No general storage interface, transaction framework, clock, background watcher, installer protocol or registry syscalls.

Record wire format is exactly 64 bytes, all integers little-endian:

- bytes 0..7: ASCII `BIMNENR1`;
- 8..9: uint16 schema 1;
- 10: phase 1 clean, 2 pending;
- 11..15: zero reserved bytes;
- 16..23: nonzero uint64 generation;
- 24..39: nonzero 16-byte public installation identity;
- 40..55: operation identity, all zero for clean, nonzero for pending;
- 56..63: zero reserved bytes.

Reject other lengths, magic/schema/phase, zero generation/installation, phase-operation mismatch and nonzero reserved bytes. This is an experimental codec, not a published cross-product ABI. Clean means only a hypothetical record phase, not proven safe networking or installer success. Pending is deliberately not split into committing/rolling-back: all are equally inadmissible. The record contains no credentials, paths, hashes or rollback payload. It does not replace the existing schema-1 foreground manifest or constitute a rollback journal.

Minimal API surface (names may follow Go conventions without broadening behavior): `Decode([]byte) (Record,error)`, `Encode(Record) ([]byte,error)`, `Evaluate(Observation) Decision`, and `AfterPendingEvent(Record, Event) (Record,error)`. Encode validates identically to Decode and cannot persist. No exported writer, Begin, Enroll, Settle or Clean constructor. Tests may directly form hypothetical clean Records.

Observation models explicit read result (protected absence, present, unsafe), view (native or other/unknown), security outcome (protected or unsafe/unknown), and two sampled record snapshots plus optional expected installation/generation binding. These are offline evidence inputs, not caller-granted authorization tokens. Do not accept a single trusted/verified boolean as a substitute for view/security/record/generation distinctions. Default/zero Observation must deny. A present record requires two byte-identical valid snapshots and protected native evidence throughout; changed identity, generation, phase, security or view denies. Expected bindings, when supplied, must match exactly; generation zero is invalid for a present record.

Decision has three orthogonal outputs: packet disposition (LegacyUnchanged or RefuseProtectedAdmission), native disposition (Unavailable, Refuse, or EligibleModelOnly), and stable reason enum: notEnrolled, cleanModelOnly, pending, unsafeEvidence, wrongView, invalidRecord, changedSnapshot, bindingMismatch. Validate evidence/view first, then decode, compare samples, compare bindings, then phase; return the first failed check in that order. Protected absence yields LegacyUnchanged/Unavailable/notEnrolled. Present clean, consistent and protected yields LegacyUnchanged/EligibleModelOnly/cleanModelOnly, never a runtime permit. Pending yields RefuseProtectedAdmission/Refuse/pending. Unsafe/unknown, malformed, stale or changed observations yield RefuseProtectedAdmission/Refuse with the corresponding reason. The packet refusal is a future participating-host model only; this disconnected package changes no real packet behavior, even for unsafe observations. No foregroundProcess input exists.

AfterPendingEvent accepts pending records only and a closed enum: hostLost, reboot, localCommitCallback, localRollbackCallback, childRemoval, rollbackDisabled, localFinalize, updaterLost. Every valid event returns the identical pending record; invalid records/events error. No event produces clean or deletes state. This small model makes the missing authority executable as a negative invariant without inventing a settlement framework. Do not add a Begin transition merely to complete a diagram.

Generation equality detects observed change, not ABA or malicious replay. Future writers must serialize, pin identities, publish pending before mutation, guarantee durable ordering and increment without wrap/reuse. Two samples are not atomic admission or rollback protection. Tests must make this limitation explicit. No production race-free reader/admission claim is made here.

## Follow-on boundary

The next PR can honestly claim strict codec validation and conservative offline decisions only. Completing enrollment requires a separately accepted architecture and proof of outer transaction authority, enforced participating-host compatibility, enrolled updater health-check/restore safety, durable publication and recovery. If those cannot be achieved within authorized packaging, native enrollment remains unavailable. No tags, binaries, assets or releases follow from this plan.

## Approved fixed-package offline prototype boundary

This 2026-10-30 amendment specifies conditional requirements for the Desktop-owned offline prototype, not a new Core production trust implementation. See [ADR 0029](adr/0029-disabled-native-enrollment-primitives.md#approved-launch-boundary-amendment-2026-10-30) for current provenance and authorization, and [prototype acceptance](NATIVE_ENROLLMENT_ACCEPTANCE.MD#offline-prototype-acceptance-amendment). Historical pure-model requirements above remain unchanged.

Native enrollment and every enrolled modification require an already fully elevated, same-user interactive initiating MSI client. Refuse before mutation and request an administrative launch when that boundary cannot be independently established. Neither the elevated MSI server nor an initiating-process claim substitutes for effective-token validation at the protected action. Ordinary nonenrolled packet installation, updater health checks, restart and rollback remain unchanged.

The prototype is limited to an exact trusted package and approved effective database allowlist. Validate the Binary DLL digest, imports, payload, action conditions and mutation-driving properties. Reject transforms, MSP patches and unapproved cached/maintenance databases. Use synchronous, checked Binary DLL actions with fixed exports. The approved MajorUpgrade removal is after InstallExecute and before InstallFinalize; all resource mutation, rollback and commit work must remain inside that transaction. A nested old-product removal must never settle the outer transaction. No resource work is allowed after Finalize.

An immediate post-Finalize callback must independently pass the effective-token gate: open the thread token first and use the process token ONLY on ERROR_NO_TOKEN. Other failures refuse; never RevertToSelf to obtain a stronger identity. Verify the expected user SID, interactive session and logon identity, elevation, integrity, enabled Administrators membership and token restrictions. Recheck the approved effective package at this boundary. Actual MSI callback token semantics have not been observed; token fixtures and static reasoning make this prototype conditional, not proof that the callback can pass safely.

Post-Finalize settlement is only a narrow protected journal acknowledgment. It performs no resource mutation and does not certify that the initiating caller received a successful MSI return. Before any durable clean publication, reacquire the validated exclusion mutex and revalidate the exact pending generation/installation/operation, final inventory and completed mutation quiescence. Durable exclusive handoff can replace continuity on one owning worker thread ONLY after all resource mutations, rollback and commit actions are quiescent. Handoff, host loss and competing admission must remain excluded by a durable pending barrier; a future validated Core barrier reader is required and is not implemented here.

A missing callback, filtered or otherwise invalid token, verification/flush failure, callback failure or death retains pending and requires explicit administrative recovery. Interrupted or reboot-incomplete outcomes cannot publish clean. This is an abnormal-failure rule, not evidence that routine success avoids manual lockout. That claim requires actual elevated MSI traces and durable-reader proof, neither authorized nor available now.

Enrollment must still reject incompatible runnable managed hosts and incompatible rollback sets. Existing enrolled updater health-check/restore requirements are unchanged and unproved; this amendment does not redesign the updater or permit early settlement for its service restart. SYSTEM and Administrators are trusted under the existing threat scope, not treated as malicious actors this mechanism can defeat. No generic bypass, completion boolean, settlement endpoint, reader, production hook or runtime enablement is added. Existing codec/model tests remain offline classifications, never package security enforcement.

This amendment supersedes the earlier registry selection, reader deferral, SYSTEM/Administrators-only storage ownership, and two-production-file limit. It does not supersede the disabled enrollment, codec or no-integration boundaries. ### A: fixed protected-file reader

Choose native Program Files, resolved using FOLDERID_ProgramFiles with flags zero, followed by exactly `Bimeron Core/NativeEnrollment/record.bin`. The space in **Bimeron Core** is canonical, matching the current Core service installation source. `BimeronCore` is not an alias. No environment path override, arbitrary-path public API, registry fallback, Desktop format interoperability or general storage framework is allowed. Preserve exactly the existing 64-byte BIMNENR1 codec and Evaluate semantics. Explicitly reject Desktop 48-byte LPF records; never reinterpret their counters as Core clean state.

Add a disconnected read-only Windows adapter inside internal/nativeenrollment. It has no initializer, production caller, enrollment, creation, write, repair, delete or settlement operation. A fixed-location read returns evidence/classification only, never an admission capability. Private fixture entry points may accept disposable paths but cannot escape into the public API or weaken validation.

Resolve the known-folder object by identity, not case-insensitive string comparison alone. Pin a local fixed-volume GUID root and every existing ancestor through the leaf using held disk-object handles without write/delete sharing; verify final volume/file identities and parent-child resolution remain consistent. Reject remote/device/alternate-stream redirection, reparses at every component, wrong object type, ambiguous identity, query failures and identity changes. A drive-letter spelling is not a root pin. Hold all handles through descriptor validation, both bounded record samples and identity rechecks; release on every exit. Read at most 65 bytes per sample to reject oversized records. Matching samples do not provide atomic admission or detect unobserved ABA.

Trust exact owner/allow principals SYSTEM S-1-5-18, Builtin Administrators S-1-5-32-544, and TrustedInstaller S-1-5-80-956008885-3418522649-1831038044-1853292631-2271478464. Require a present non-null protected DACL on the enrollment container and record. Validate all ancestors for effective untrusted replacement/mutation, allowing normal inherited ancestor descriptors only if their actual rights are safe. Inspect actual Windows descriptors; expand file/directory generic rights and reject untrusted data/append, EA/attribute writes, delete-child, delete, WRITE_DAC, WRITE_OWNER and generic write/all. Read-only rights are harmless. Do not subtract deny ACEs to justify an otherwise unsafe allow. Reject unfamiliar effective ACE forms and unreadable/malformed descriptors; handle inherit-only ACEs deliberately. Existing control.protectedDescriptor is a reference, not permission to import its private code or silently inherit its weaker protected-DACL/identity assumptions.

Trusted bootstrap absence requires an exact not-found beneath a validated, held nearest existing ancestor with the remaining fixed suffix unable to be created/replaced by untrusted users. An absent Bimeron Core or NativeEnrollment subtree can therefore mean non-enrollment only after validating that ancestor chain. A missing record.bin inside an EXISTING NativeEnrollment container is unknown/unsafe, never bootstrap absence. Access denied, sharing failures, broken chains or unexplained disappearance deny. Administrator deletion of the entire enrolled subtree can be indistinguishable from bootstrap absence: this limitation remains explicitly unsolved. No historical-enrollment detection, rollback resistance or malicious-administrator defense is claimed.

Positive security fixtures must construct actual Windows security descriptors in memory and feed the real descriptor parser. Native trusted protected-file positive coverage unavailable without privileges must be reported as unavailable, never replaced with a synthetic passing native test. Disposable user-owned negative fixtures may prove rejection only.

### B: operation outcomes and read-only health proof

Keep all production updater code unchanged, including shared Linux helpers. Actual call graph: Windows service update invokes updateWindowsService, stages/verifies the candidate, snapshots SCM Running/Stopped, stops, then calls replaceServiceExecutable with activation/deactivation callbacks. Running activation starts, waits for SCM Running, then waitUpdatedService validates IPC hello through validateUpdatedHello. Stopped activation returns without start or IPC probe. On replacement/activation rollback, restorePreviousService restarts only when errUpdateRolledBack and previously running; its Windows callback waits ONLY for SCM Running and does not IPC-probe the restored binary. Linux also calls these shared helpers, so changing them would broaden this task.

Define a small disconnected operation descriptor binding nonzero installation, pending generation and operation identities, exact candidate and rollback image identities/digests, expected role/version/protocol, and original running/stopped state. Reject missing, zero, conflicting or stale bindings. Outcomes distinguish candidate health success, activation/health failure with restored-running observation, restored-stopped observation, blocked rollback/retained backup, and incomplete/unknown execution. An observed outcome never produces clean, authorizes restart, or permits networking.

Model future read-only health separately from ordinary service dispatch: a separately accepted startup gate would be required before any runtime use. This task adds no listener, process launch, command or gate integration. Pending is never bypassed for ordinary dispatch/network access, and settlement before health is forbidden. Bind a fresh nonzero challenge to the exact operation, installation/generation, OS-authenticated PID plus creation time, expected role, version/protocol and independently observed held-image volume/file identity and digest. Missing identity fails closed. A response's self-reported hash/version alone is not authenticated image authority. Reject replayed/stale challenge, PID reuse, wrong image/role/operation and incomplete evidence. These are offline evidence inputs, not a caller-supplied verified boolean.

Use a TEST-LOCAL pending ledger to model crash/failure ordering around the actual file helpers; do not implement a production transaction coordinator. All interruptions, failed identity/health, restored old hosts and updater death leave pending unchanged. Compatibility-negative cases require an explicit COMPLETE approved runnable-host AND rollback-image set; unknown/incomplete sets or one incompatible member refuse the proof. An approved list fixture is not enforcement against later old-host return. Neither this proof nor the reader settles state or grants a runtime permit.
