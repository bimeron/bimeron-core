# Core maintenance contract design

Status: PROPOSAL for review, 2026-11-04. No production API is implemented or authorized by this document. Source baseline: Core `7cc55f07ce2c48be4071b155c3dd58cf925a88ae`. Parent planning uses Sol MEDIUM; independent source audit and model implementation use explicit Sol LOW through `codex_2`.

Inputs: S's approved `docs/workstreams/daemon-servicing-recovery/hosting-proposal.md`, `model-results.md` and `scripts/servicing-model` in the read-only sibling macOS worktree, completed model commit `506106642970cb78fa4c7f963ebca0f0bf0f64ce`. Its 27 tests are model evidence, not OS proof. The approved target is a separate root owner and explicit root CLI, future fresh-capable installations, fail-closed manual reboot recovery, one backup, no owner self-update and two-stage uninstall. None of those constraints is reopened here.

## Capability and trust boundary

Keep public protocol 1 and `daemon_session_guards` unchanged. Require a separate exact capability `core_maintenance_contract: 1` plus supported gate, dirty-resource and result schema versions, obtained from a root-only maintenance endpoint. Public hello may expose a sanitized capability and gate state; it grants no authority. Missing fields, unknown versions or absent endpoint mean unsupported servicing, never fallback to public shutdown or unguarded requests. Existing installations are not migrated implicitly.

The endpoint accepts kernel-authenticated UID 0 before parsing; Core clients also verify the server's kernel root identity and protected fixed endpoint ancestry. Bind installation identity, protected owner installation record and process identity; a caller-supplied UID/PID/path is never evidence. The selected owner executable identity/digest policy is an installation binding, not something a socket peer UID proves. Root may impersonate root: this is no cryptographic attestation against malicious administrators. Exact secure-file and peer/process adapters remain acceptance prerequisites. Ordinary configured control UID, session guards and GUI identity confer no maintenance right. No arbitrary paths, commands, config, passwords or network requests belong in maintenance messages.

## Identities and records

All names below are proposed schema-1 fields, not additions to the current Request type. UUIDs are canonical lowercase strings; generations and sequences are nonnegative bounded integers, rejecting overflow. Installation UUID survives update, never implicit recreation. Generation increases on accepted maintenance intent; sequence increases within an operation. Operation UUID identifies immutable action/digests/authorization scope. A transport request UUID identifies one command/payload, separate from operation UUID. Exact duplicate returns the recorded result; conflicting reuse is rejected before effects.

Target identity is `(installation_id, operation_id, generation, boot_id, instance_id, session_expectation)`. Session expectation is a tagged `{kind: idle}` or `{kind: active, id: UUID}`; missing, null or empty session is invalid. Producer identity includes current boot and random per-process instance, separately from the original target. Kernel process binding includes boot, PID and process start identity; PID alone is insufficient. Readiness additionally binds build/artifact-set digest, exact capability/schema set, challenge and current producer. Never rewrite the original target when adopting a recovery producer.

Owner alone writes one authoritative gate/journal projection: schema, installation, generation, operation, action, sequence, phase, expected target, installed/candidate digest, recovery policy and owner binding. Core never edits it. Core alone writes dirty-resource evidence and immutable result records. Each result references the exact gate sequence/digest read. Owner terminal records may retain an operation while the gate denies admission pending release. A torn, absent required, corrupt, oversized, rollbacked or incompatible record means RecoveryRequired. An installer must explicitly establish a clean fresh installation; missing files are not clean defaults.

## Admission and ordering

Every fence-aware Core boot starts sealed before exposing any mutation path. It validates installation/gate and all dirty evidence, even when no maintenance journal exists. Status and recovery may be available while sealed. Gate pending, removal pending, invalid storage or unresolved dirty evidence prohibits starts. A committed record with another boot/instance also prohibits starts pending reconciliation below.

All guarded and legacy starts re-read gate under common command admission before loading configuration or calling Start. Every engine entry path capable of resources must use the same durable dirty barrier; protecting the RPC alone is insufficient. Before backend Acquire, Open, DNS, routes, adapters or retry-side mutation, persist an intent binding session and resource ledger revision. For each resource record planned identity, prior observed state, intended owned change and outcome; flush intent before effect and retain ambiguous intents after crash. A session-wide dirty bit alone cannot describe safe recovery. Retry attempts extend the ledger and never clear it between attempts. Failure to persist means no next effect and admission stays sealed.

Owner publishes durable gate before shutdown. A start already admitted may finish crossing its dirty barrier; shutdown must compare the actual current session under admission. Mismatch closes the gate but does not stop the unexpected session: require renewed explicit interruption consent. A maintenance shutdown seals starts before waiting for Stop, and never reopens on failure, expiry, disconnect or timeout. Public stop may finish existing cleanup while fenced; public shutdown must not bypass result publication or authorize replacement.

Lock order: owner transaction.lock -> durable owner publication -> IPC; Core command admission -> short Engine state mutex. Core never takes transaction.lock. Do not hold Engine state mutex while waiting for Stop, performing persistence, OS cleanup or callbacks. A Core ledger/result writer serializes revisions but must not call back into command admission. Cleanup worker can persist its result without acquiring command admission held by its waiter. Snapshot state, release Engine mutex, perform writes, then publish using a checked revision. Owner does not hold a Core mutex across filesystem/service work. Read-only queries must remain possible during cleanup. A production implementation must document the concrete lock graph and test blocked callbacks and cancellation, rather than copy these roles into nested locks blindly.

## Commands and results

Every mutation carries contract version, request UUID, operation UUID, expected generation and target/binding; unknown/duplicate/noncanonical keys are rejected. Recommended frame limit 64 KiB, no caller-controlled record path. Validate kernel authority before parsing, then framing/schema, installation/owner binding, operation/generation, boot/instance then session, then phase. Failed validation has no resource effect. Return a bounded typed result with current sanitized identity; never leak profile data.

- `maintenance_status`: exact versions, build digest, installation/generation/sequence, current boot/instance/session, gate phase, dirty summary and retained result IDs. No empty-engine cleanliness inference.
- `maintenance_shutdown`: validate durable intent and exact target, seal, cancel session and await actual cleanup completion independent of caller lifetime. Return accepted/pending or durable result reference. Failed cleanup remains sealed. Repeated exact request joins/query existing work, never executes Stop twice as a new operation.
- `maintenance_query`: operation plus optional request/result ID; returns retained immutable outcomes and current progress. Lost reply means query, not a new operation. Query does not resume or release.
- `maintenance_recover`: explicit root approval scoped to existing operation and retained ledger revision; recovery-only execution without Start or VPN reconstruction. Reconcile each intended effect against current OS state; external conflicts or unknown ownership block rather than overwrite. New boot proves old processes gone, not DNS/routes restored. Never turn an empty ledger from a fresh engine into proof of an older dirty session.
- `maintenance_release`: validate terminal owner record, current producer binding, fresh challenge/readiness, compatible schemas and no unresolved ledger; durably record release result before opening admission. Re-read owner projection under admission. No implicit VPN start. After reply loss query release outcome. If release record persisted but process died before opening, startup requires fresh current reconciliation rather than trusting prior readiness.

A cleanup result contains schema/result UUID, full original target, current producer, gate sequence/digest, ledger identity/revision, completion sequence, session inactive/disconnected observation, per-resource outcomes and overall `succeeded|failed|recovery_required`. Success requires all owned resource teardown/restore invariants, worker completion, released session ownership and durable result publication. Include explicit `not_acquired` only when the ledger proves it; never treat missing evidence as not applicable. Failure retains residual identities and bounded error codes. If result write/flush fails, no success response is permitted, dirty intent remains; storage may prevent recording failure itself. A later query must report unknown/recovery-required rather than synthesize success.

Core cleanup receipt covers Core-owned resources only: DNS changes, route/bypass entries, adapter/packet stack/transport workers and backend locks for that ledger. It does not attest service disable, process exit, executable replacement, trust or owner cleanup. The source does not yet support that complete invariant. Exact resource postcondition checks must be implemented/reviewed before advertising the capability.

Owner replacement requires BOTH durable scoped successful cleanup and independent exact process exit, with restart exclusion held through publication. Endpoint disappearance, inactive session, Stop return, bootout or disable alone does not prove both. For launchd-owned Core, owner must validate nonchild kernel exit association, never waitpid. A lost observer in the same boot blocks replacement: no PID-absence adoption. A new recovery Core itself must exit with observation if its executable will be replaced. Starting any candidate invalidates prior exclusion/exit/readiness evidence.

## Committed-operation reboot and new-instance reconciliation

S's model intentionally blocks changed-identity release after commit. Three options:

1. Reuse committed readiness across reboot: best availability, but stale process/build/resource proof. Reject.
2. Automatically bind a fresh instance and release after a new handshake: less downtime, but expands post-crash authorization and risks same-boot adoption. Defer to a separate architecture decision.
3. Keep committed artifacts and generation immutable; add a durable reconciliation subrecord with explicit root resume, recovery and fresh current readiness. Recommended for the approved manual-recovery target. This is a production decision pending user approval; model selection is only a prototype assumption.

Exact proposed option 3 sequence:

1. On committed startup, keep admission closed. Owner verifies the committed complete artifact set, installation, compatible ledger/result schemas and retained original authorization. No republishing or backup replacement merely to refresh identity.
2. Root resume specifies committed operation/generation/digest and expected current producer; owner persists reconciliation intent with new sequence. Same-boot changed-instance after lost observation remains blocked until reboot. Same current instance after owner restart may re-handshake, but only if original exact process association is retained; otherwise use reboot. A new boot proves prior boot exit only.
3. Run Core recovery-only with retained target/ledger. Persist a new result binding old target and current producer. Unknown prior mutation, corrupt ledger or external conflict remains RecoveryRequired. For an originally idle clean installation, prove ledger coverage, not just disconnected status.
4. Owner verifies current process/build against committed bytes, exact maintenance/recovery schemas, inactive session and clean ledger using a newly issued one-use challenge. Prior readiness is invalid even if the same artifact digest is present. Keep the owner gate closed throughout. Restart exclusion for any replacement remains separate from control-readiness startup.
5. Owner durably writes a release-authorized subrecord with new producer, result reference, challenge digest and sequence, without changing original operation or artifact generation. Core compares all fields and rechecks clean state under admission, durably records its release result, and keeps admission sealed. Owner finalizes outcome by querying that result and durably publishing release finalization; admission remains gated until that finalization is revalidated. Any crash before finalization retains reconciliation identity and requires current handshake again; exact old queries remain readable but cannot release a different instance.

After already-released normal reboot, a fresh runtime admission check still validates installation, terminal gate and clean ledger; old readiness is never a startup credential. Dirty ordinary sessions require recovery even with a terminal maintenance operation. Removal has no release-to-start transition.

## Errors, expiry and retention proposal

Errors are stable codes: `unsupported_contract`, `invalid_request`, `unauthorized`, `installation_mismatch`, `owner_binding_mismatch`, `stale_generation`, `operation_conflict`, `stale_instance`, `stale_session`, `maintenance_pending`, `cleanup_pending`, `cleanup_failed`, `recovery_required`, `storage_failed`, `history_full`, `expired_challenge`, `readiness_mismatch`. Pending is not failure or permission to retry with weaker guards. Responses include retry disposition `query|new_plan|manual_recovery|unsupported`, not a blanket retry boolean.

Proposed challenge lifetime: 60 seconds on the issuing boot's monotonic clock, one use, tied to root peer and operation/producer/sequence. Restart, boot change, identity/sequence change or reuse invalidates it. Wall-clock change never extends it. Accepted operation authorization and dirty fences do not expire; transport cancellation stops waiting only. No deadline permits force cleanup, replacement or gate clearing.

Proposed initial bounds: one active maintenance operation; at most 256 retained terminal operation records and 64 KiB per summary, with a bounded separate resource ledger whose exhaustion blocks before another effect. Retain unresolved ledgers/results, current and previous artifact generation references and current operation regardless of age. Reject new work on capacity exhaustion rather than evict replay identity. First implementation can deliberately stop at capacity: compaction is additional reviewed work. A later explicit root archival design must retain nonreusable operation tombstones or an authenticated epoch/high-water scheme so forgotten IDs cannot replay. Queries outside retained history return unknown, never not-executed. Numeric bounds and challenge lifetime require review and parser/storage tests; the small model uses configurable capacity and no real clock/parser.

## Source insertion map and limits

At the baseline, `internal/control/server.go:222` serializes start/stop/shutdown; `:241` checks session guards; `:346` checks closing before config load; `:372` calls Stop and `:375` sets closing only on success. Add fence validation and maintenance admission here in a later approved change, including legacy paths. `daemon_guards.go:5` rejects shutdown guards; do not reinterpret this as maintenance. `server.go:401` is existing wire validation; use a separate maintenance schema/parser and root endpoint.

`cmd/bimeron/daemon_unix.go:15` creates listener and engine without a durable startup gate. `internal/control/socket_unix.go:26` allows root OR configured UID; it is unsuitable as-is for the root-only endpoint. Its Close at `:40` releases daemon.lock before final engine cleanup; that lock is not restart exclusion. `server.go:162` closes listener/waits workers/final Stop; `:431` cancels Serve after attempted shutdown response, not after process exit.

`core/engine.go:180` Start and `:286` backend Acquire need durable dirty admission before effects; direct Engine callers must be covered. `:317` observes Close failure; `:280` eventually clears active even after errors. `:223` Stop timeout only stops waiting. `core/runtime.go:371` runs cleanup actions once in reverse order, reports generic failure, and provides no durable scoped receipt.

`core/platform_darwin.go:41` Acquire calls macnet Recover; Open creates utun/stack and registers recovery. Adapter Close wrappers return nil without postcondition verification. `internal/macnet/manager.go:141` saves existing state with file Sync; `:373` Configure and `:445` Recover own network state, including DNS conflict handling. These are useful recovery components, not the proposed installation/session ledger or proven power-loss protocol. No complete resource coverage, directory flush semantics or safe new-instance readiness guarantee follows from them. `cmd/bimeron/developer_record_other.go:5` is a no-op on Darwin: developer records are not this contract. Windows foreground/protection contracts remain separate and must not be advertised as macOS servicing support.

## Staged production plan and decisions

This local work creates no issue/PR/CI activity under the explicit pause. A future separately approved implementation should first resolve option 3, record namespace/authority, exact ledger coverage/postconditions, bounds and compatibility matrix in an accepted ADR. This document records alternatives without marking acceptance.

Stage 1: pure schema/admission and persistence interfaces with fake storage; cover legacy and direct callers, cancellation and all write boundaries. Stage 2: Core dirty ledger and resource-specific recovery/result implementation with mocked backend faults and lock-order tests; advertise nothing until complete. Stage 3: peer/file/durability adapters and startup integration, reviewed independently; no privileged owner yet. Stage 4: cross-repository owner contract integration and fake service/process tests, including commit/reboot release, rollback and two-stage removal. Stage 5: separately authorized disposable-Mac acceptance for real process identity, exit observation, persistent restart exclusion, resource conflicts and power interruption; CI/security/trusted delivery gates precede rollout. No production rollout or privileged owner implementation is authorized here.
