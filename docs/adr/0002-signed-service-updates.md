# ADR 0002: Signed manifests and service update health checks

Status: amended, November 19, 2026.

## Context

The public release contains architecture-specific ZIP files and SHA256SUMS, but no authenticated compatibility policy. SemVer cannot state IPC, GUI, or profile compatibility. A process that reaches SCM/systemd's running state may still expose an unusable IPC endpoint. The GUI and installed service run across a privilege boundary.

## Decision

Publish a JSON manifest and detached Ed25519 signature. Sign the exact UTF-8 file bytes, including its final newline. The manifest includes a key identifier derived from the public key's SHA-256 and archive hashes computed after ZIP creation. Compatibility values live in `release/compatibility.json` and require review on every release. The GUI pins public keys and checks the signature, compatibility, ZIP size and hash. It elevates a trusted core bundled in its installed, administrator-owned package and passes the downloaded executable's path, SHA-256, and expected version as arguments. The privileged updater copies the untrusted file as data into the protected directory, checks staged SHA-256, Go identity, and architecture before stopping the service, then requires IPC `hello` with the expected version and protocol after restart. It never elevates a downloaded executable before checking it. Existing old services can be updated only after the GUI package bundles this new updater.

Rotate keys by shipping a GUI version that trusts both old and new public keys before changing the release signing key. Later remove the old public key after its supported release window. Old GUI versions must update before they can trust releases signed only by the successor key. A compromised signing key still requires a separate incident response and GUI trust-store release; rotation alone does not revoke an already installed trust anchor.

Since November 19, 2026, release signing keys are non-exportable Ed25519 keys generated inside the OpenPGP application of two YubiKeys: key A signs, key B is the backup, and both require the PIN and a touch for every signature (touch policy `fixed`). The publisher sends the complete manifest bytes to the card, which returns a plain Ed25519 signature, so the manifest and signature formats and all verifiers stay unchanged. Signing refuses manifests above 2560 bytes, below the card's 3070-byte input limit. The rotation away from the software key `7370a2d8cf890e5e` was precautionary: it may once have been stored as a CI secret. Desktop 0.3.1 is planned to pin the old key and both hardware keys; Desktop 0.3.0 and earlier pin only the old key, so the first hardware-signed release follows the Desktop 0.3.1 release and sets `gui_min` to at least `0.3.1`. No release after `v0.4.0-beta.2` uses the old key, the publisher enforces each key's release range, and Desktop drops the old key after releases it signed leave the supported update window. Core repair acquisition, which fetches only its own exact release, pins only the hardware keys. [RELEASE_KEYS.md](../RELEASE_KEYS.md) is the authoritative key list. These are the hardware keys `H1` (A) and `H2` (B) of ADR 0040; until that design is implemented, schema 1 manifests carry a single hardware-key signature.

Backfill, which signed metadata for an existing release from its downloaded assets, is retired. Those assets and their SHA256SUMS come from the same release, so nothing tied the archives to the tag commit; a signature now covers only bytes prepared locally from a reviewed commit and checked by the publisher (ADR 0003). No backfilled manifest was ever published: every release since `v0.1.0-beta.3` shipped its manifest through the prepared-release path, and `v0.1.0-beta.1` and `v0.1.0-beta.2` predate the update contract. The retired software key only verifies the published manifests it signed.

## Alternatives and tradeoffs

- GitHub asset digests alone depend on GitHub as the sole trust root and do not authenticate the compatibility policy outside its API. Ed25519 lets the GUI verify downloaded metadata independently.
- An embedded signing key in the core would make rotation depend on core updates and would put the trust decision inside a privileged executable. The GUI owns update selection and pinned public keys; private keys stay outside the repository and CI, and signing happens locally on prepared bytes (ADR 0003, RELEASE_UPDATES.md). Core repair acquisition embeds only the hardware verification keys for its own exact release. ADR 0040 reverses this alternative for the core store by embedding verification keys in Core.
- A software private key alone, even in an offline vault, lets any copy of it sign, and its exposure history is hard to prove. Non-exportable hardware keys need the operator, PIN, and touch for every signature; two devices avoid a single point of loss. ADR 0040 later adds an offline release key `R2` alongside the hardware keys in a multi-signature policy.
- YubiKey PIV Ed25519 requires firmware 5.7 or newer; the available devices run 5.4.3, whose OpenPGP application supports Ed25519. Signing through an OpenPGP tool would wrap a hash in OpenPGP packets and change the signature format; raw card signing keeps it.
- Automatically reconnecting VPN after update would need persistent secrets and recovery of session intent. Explicit reconnection preserves current service behavior.
- A stopped service cannot answer IPC without changing its prior state. It stays stopped; executable identity and staged digest are checked before replacement, and the first later start is user initiated.
- Elevating the downloaded executable would allow a same-user file swap between the GUI's verification and process launch. Elevating the bundled updater avoids this race, but requires the GUI package directory to be protected against ordinary-user writes. Portable or user-writable GUI installations must disable this update route.
